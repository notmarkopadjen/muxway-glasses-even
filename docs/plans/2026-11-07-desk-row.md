## 1. Goal

The hub keeps the **desk**: the view the owner's clients share, which
panes are open as tiles and which is focused, or the window the window
view shows (`GET /v1/desk`). The web and Android write it as the view
changes. The guideline says what the small clients do: open the desk's
focused pane from their lists, and nothing else: they read the desk
and never write it.

Goal: a `desk` row at the top of the pane list, before the inbox's,
that opens the desk's focused pane: the first of its panes when none is
focused; for a window desk, the focused pane, else the first listed
pane of that window. The row names the pane it opens; the desk's pane
that is not in the listing is not opened. The row is there only while
the desk holds a pane (a desk is never written empty, so a desk
without panes is the hub's own before any client wrote one, and spends
no row on a nine-row list); a desk whose panes are none of the
listing's shows the row with `nothing to open` and a tap says so. The
app follows the hub's `desk` event: the row changes within a second of
another client's change. Out of scope: writing the desk, the
arrangement, the minimised row, opening several panes at once (the
columns are the wearer's own selection), a desk entry in the menu.

## 2. Design

`src/api.ts`, `src/protocol.ts`, `src/app.ts`, `src/views.ts`.

- `api.desk(etag)`: `GET /v1/desk` as JSON with `If-None-Match`; the
  answer carries an `ETag`, and a `304` costs nothing.
- `parseDesk(body)`: `view` (`panes` or `window`, else no desk),
  `panes` (addresses by the grammar, the first four, no repeat),
  `focused` (an address, else none) and `window` (`host/session/window`
  by the grammar, else none); anything else in the body is ignored.
- The app reads the desk with every listing (every ten seconds, on
  every event, and a `desk` event is one: `parseEvents` reports it,
  `runEvents` asks for the listing). A hub that answers `404` has no
  desk: asked once, as the feed is.
- `deskPane()`: the pane the row opens, from the latest listing. View
  `panes`: the listing's pane at `focused`, else the first of `panes`
  that the listing has. View `window`: the listing's pane at `focused`,
  else the listing's first pane of that window. None: `nothing to
  open`. The model carries it as `desk: { pane: Pane | null } | null`
  (`null`: no row).
- `listLayout`: the row `» desk · <name>` first, with the pane named as
  its own row names it (alias or program and status, `V.nameParts`),
  or `» desk · nothing to open`; the row is a `ListItem` of kind
  `desk`. A tap opens the pane as a row's tap does (`openPane`, which
  wakes a parked pane: the owner came back to it); with nothing to
  open a note in the hint, `the desk's panes are not in the listing`.
  In selection mode the row has no box and a tap does nothing, like
  the inbox row.

## 4. Security analysis

- Read only: the client never sends `PUT /v1/desk`; S67 checks that no
  request to `/v1/desk` but `GET` ever leaves the app, with a hostile
  desk as with a sound one.
- `GET /v1/desk` needs a read grant; the hub answers the panes the
  principal may read and leaves the rest out, so a read-only token
  sees a desk of the panes it reads and opens one as it opens any row.
  An observer of a share has none (`401`, which the app treats as any
  refused token: forgotten).
- The desk crosses a trust boundary: its body is parsed with caps
  (four panes, the grammar for every address, strings cut), and the
  row never shows a string of the desk's: it names a pane of the
  *listing* that the desk points at, or `nothing to open`. A desk that
  names a pane the listing lacks opens nothing; a desk of a thousand
  panes, of junk, or of a megabyte is the first four addresses that
  pass, or no desk.
- Opening a pane from the desk is the listing's `openPane`: a parked
  pane is woken with the host's `later` call, as from the row; nothing
  else is sent.
- Logged: `GET desk 200 2 panes`, never the addresses or a pane's rows.
- No new dependency.

Deviations: none in the client. A gap in the core, found by F71's
first run: the hub answers the browser's CORS preflight only for the
paths in `corsPath` (`internal/hub/cors.go`), and `/v1/desk` is not
among them, so a page on another origin, which this app is, cannot read
the desk at all (`Load failed` on the preflight; the web client never
met it, since the hub serves it from its own origin). One line fixes it:
`/v1/desk` in that list. It was not made here, the core being another
repository; it is reported with the pull request. Until it lands, a hub
on the core's main shows no desk row on the glasses (the screens page
says so), and S67 and F71 fail against it (run 20261107-105045-567e529).
A test lesson, not a deviation: the desk names windows by index, so a
test that writes a desk for the `build` window names `work/1.0`, not
`work/build.0`; the hub took the latter and the listing never matched
it.
