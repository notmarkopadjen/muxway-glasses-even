# Feature: the gestures go to a container with nothing to scroll

> Status: proposed. The owner's report of 2026-11-03: the footer moves a
> little with every scroll on the list and the pane, not on the answers.
> On top of the rules (#46, `2026-11-03-rules.md`).

## 1. Goal

On a page without an OS list the hint is the container that takes the
gestures, and the firmware scrolls the text of the container that takes
them: the footer moved with every scroll on the list and the pane, and
boxing it with exactly one line inside (the banner's shape) did not stop
it. The answers, the confirmation and the inbox are OS lists, whose list
container takes the gestures, and their footer stands still; the pane's
title stands still because it takes nothing. The SDK has no switch for
this: a text container either takes the gestures and scrolls, or does
not take them. So the gestures go to a container that has nothing to
show: the footer and every other container then stand still, as on the
answers.

## 2. Design

A block may be the page's **catcher**, `capture: true`: `src/glasses.ts`
sets `isEventCapture` on it and leaves the hint's off. The catcher has
no text, so whatever the firmware scrolls, nothing moves on the screen.

- **The pane and the columns**: the rule under the title is the catcher.
  It is there on every pane page, two pixels high, with nothing in it.
  Three columns fill the page's eight containers, so no block can be
  added there, and the rule is the one with nothing to show.
- **The boxes** (the suggestion, listening, transcribing, failed, heard):
  a catcher of their own, `gesture`, 16 × 16 px in the top right corner
  with no border and no text, invisible; the title rows end 20 px short
  of the edge to leave it room.
- **The pane list**: seven rows and the hint are the page's eight
  containers, so no catcher fits beside them. The rows become one block
  of lines at the font's own pitch, 28 px, which holds **nine** rows
  where seven stood at 36 px, and the corner catcher sits beside it; the
  row text is at most 490 px, so the block's width of 554 px loses
  nothing. The cursor stays the `>` mark; the cursor row's extra
  brightness goes, since one block has one brightness, and the mark is
  what the owner found the row by (the brightness alone was missed, the
  comment in the code says). The window of rows under the cursor is the
  same as before, nine deep.

```
┌──────────────────────────────────────────────────────────┐ ▪ ← the catcher, 16 × 16, black
│ > ◐ build · Claude · working                             │
│   √ tests · bash · done                                  │   nine rows, one block
│   …                                                      │
├──────────────────────────────────────────────────────────┤ ← the hint's box
│ ▽ move · ● open · hold to select · ×× exit               │
└──────────────────────────────────────────────────────────┘
```

A cursor move is a text change of the one block, an in-place upgrade
as before; a page with fewer panes than rows leaves the block's last
lines empty.

The simulator reports gestures from whichever container takes them, so
the suite holds the pages' behaviour; only the device shows a footer
that stands still, which is the owner's check.

## 3. Protocol and API changes

None.

## 4. Security analysis

None: layout only. The catcher carries no text, so nothing from the hub
reaches it. S30's listing of two hundred panes draws nine rows now, and
the row budget (490 px, 63 bytes) is unchanged.

## 5. Privacy check

The plan, the docs and the tests name the test environment's panes; no
host, person or secret.
